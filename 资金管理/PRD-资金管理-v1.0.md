## 1. 背景与目标

### 1.1 背景

启泰数智模具配件 B2B 商城，财务模块长期存在 3 个问题：

1. **资金流水 vs 收支明细混淆**——历史做法是把"订单列表"硬塞进收支明细页，待支付、已取消的订单都列出来，最后对账对不上。
2. **销售统计口径不统一**——铸件是定制品（按客户来图时间组织生产），标准件是现货（按支付时间算），但旧系统一律按"订单创建时间"统计，账期客户差异巨大。
3. **坏账没有管理路径**——账期客户到期未还款，过去只能人工 Excel 标记，销售总额虚高，无法反映真实回款。

### 1.2 上线后影响

- 财务对账准确率从约 70% 提升到 95%+
- 销售统计支持"按支付时间/来图时间"双口径，铸件销售时点判断更准
- 坏账独立标记，老板看报表不被虚高数字误导
- 退款失败可追踪可重试，减少资金风险

### 1.3 目标

| # | 目标 | 衡量指标 |
|---|------|---------|
| 1 | 收支明细页只展示"钱真发生过"的事件 | 待支付/已取消订单不出现 |
| 2 | 销售统计支持 4 维度 + 铸件双时间口径 | 按时间/客户/商品/支付方式/渠道均可拆分 |
| 3 | 坏账有独立状态机和操作路径 | 财务可手动勾销，销售总额自动剔除 |

## 3. 功能需求

### 3.1 模块一：资金流水（fund_flow）

#### 3.1.1 功能描述

展示每一笔"钱真实发生过"的事件，**待支付、已取消的订单不计入**。收支明细页是商家最常用的对账入口。

#### 3.1.2 字段说明（数据库表 `fund_flow`，30 字段 / 7 组）

| 组 | 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|---|
| **① 核心标识** | `flow_id` | bigint | KEY | 主键，自增 |
| | `flow_no` | string(20) | * | 业务编号，规则 `LS + yyyymmdd + 序号`，如 `LS20260711001` |
| **② 资金信息** | `direction` | enum | * | `income` 收入 / `expense` 支出 |
| | `flow_type` | enum | * | `order_payment` / `order_refund` / `adjustment` |
| | `amount` | decimal(15,2) | * | **永远正数**，方向靠 `direction` |
| | `currency` | string(8) | ○ | 默认 `CNY` |
| | `fee` | decimal(15,2) | ○ | 手续费 |
| | `actual_amount` | decimal(15,2) | ○ | `amount - fee` |
| **③ 关联实体** | `order_id` | string(20) | * | 关联订单号 |
| | `payment_id` | string(20) | *（催收回款场景除外，见§4.1，不挂原支付单） | 收入填本笔支付单；支出填**原支付单** |
| | `refund_id` | string(20) | ○ | 仅 `direction=expense` 时填 |
| | `settlement_id` | string(20) | ○ | 已纳入结算时挂上 |
| | `statement_id` | string(20) | ○ | 对账后挂上 |
| **④ 业务维度** | `customer_id` | string(20) | * | 客户 ID |
| | `customer_name` | string(100) | * | 冗余存储 |
| | `sku_id` | string(20) | ○ | 商品/SKU ID |
| | `sku_name` | string(100) | ○ | 冗余存储 |
| | `category` | enum | * | `standard` / `casting` / `software` / `other` |
| | `channel` | enum | * | `miniprogram` / `pc` / `offline` |
| | `pay_method` | enum | * | `online` / `credit_period` / `offline` |
| **⑤ 时间字段** | `biz_time` | datetime | * | 订单创建时间 |
| | `pay_time` | datetime | * | 客户付了款的时间 |
| | `fund_time` | datetime | * | **钱实际到账**。线下 = 财务审核通过；账期 = 客户实际打款 |
| | `refund_time` | datetime | ○ | 仅 `expense` 时填 |
| **⑥ 状态字段** | `fund_status` | enum | * | `received` / `reversed` / `bad_debt` / `refunded` / `failed` / `pending` / `processing`（2026-08-08补充：后两个是退款流程中会用到的状态，原枚举漏写，§7.4验收标准的查询语句已经在用这两个值） |
| | `reconcile_status` | enum | ○ | `unreconciled` / `matched` / `abnormal` |
| **⑦ 审计字段** | `created_by` | string(50) | ○ | 系统自动生成填 `system` |
| | `created_at` | datetime | * | 创建时间 |
| | `updated_by` | string(50) | ○ | 最后修改人 |
| | `updated_at` | datetime | * | 最后修改时间 |
| | `remark` | string(500) | ○ | 备注（调账/坏账时必填） |

#### 3.1.3 列表页字段（9 列）

| # | 字段 | 展示 | 来源字段 |
|---|---|---|---|
| 1 | 流水编号 | 蓝色 mono 字体，点击看详情 | `flow_no` |
| 2 | 入账/退款时间 | 时间降序 | `fund_time` |
| 3 | 方向 | 🟢收入 / 🔴支出 pill | `direction` |
| 4 | 金额 | 收入 + 绿，支出 - 红 | `amount` + `direction` |
| 5 | 关联订单 | 蓝色 mono 字体，跳转订单详情 | `order_id` |
| 6 | 客户 | 文本 | `customer_name` |
| 7 | 分类 | 标签 pill | `category` |
| 8 | 支付方式 | 彩色 pill | `pay_method` |
| 9 | 状态 | 5 种颜色 pill | `fund_status` |

#### 3.1.4 筛选条件

- 流水编号、关联订单号（精确匹配）
- 客户/企业、商品分类、支付方式、渠道
- 资金方向（全部/收入/支出）
- 入账时间（日期范围）

#### 3.1.5 工具栏 Tab

- 全部 / 仅收入 / 仅支出

#### 3.1.6 规则约束

- `amount` 永远正数，方向靠 `direction`，**不能用正负号** —— 对账会乱
- 列表底部导出 Excel 按当前筛选条件导出
- 待支付、已取消的订单**不进入**资金流水表

#### 3.1.7 异常情况

| 场景 | 处理方式 |
|---|---|
| 线下打款凭证模糊 | 财务审核失败，原支付单状态改"审核失败"，可重新提交 |
| 退款通道返回失败 | `fund_status` 置为 `failed`，操作栏显示"重新退款"按钮 |
| 财务勾销坏账 | 收入行 `fund_status` 从 `received` 改为 `bad_debt`，记 `remark` 留痕 |

### 3.2 模块二：销售统计

#### 3.2.1 功能描述

聚合视图，**不落表**，实时从 `fund_flow` SELECT GROUP BY 计算。按 4 个维度拆分统计，支持铸件的双时间口径切换。

#### 3.2.2 统计维度（4 个）

| 维度 | 维度值 | 备注 |
|---|---|---|
| 按时间 | 2026-07 / 2026-W28 / 2026-07-13 等 | 默认按"支付时间"；铸件可切"来图时间" |
| 按客户 | 客户名 | |
| 按商品分类 | **全部**（标准件+铸件+软件）/ 标准件 / 铸件 / 软件 / 其他 | "全部" = 3 类合计 |
| 按支付方式 | 在线支付 / 账期支付 / 线下打款 | |
| 按渠道 | 小程序端 / PC端 / 线下 | |

#### 3.2.3 时间口径（铸件特殊）

| 口径 | 字段 | 适用分类 | 用途 |
|---|---|---|---|
| 支付时间（默认） | `fund_time` | 全部 | 财务对账、销售入账统计 |
| 客户来图时间 | `order.drawing_received_at` | **仅铸件** | 销售订单需求时点统计 |

切换"来图时间"时：标准件/软件仍按 `fund_time` 统计（不可切换）；铸件改按 `drawing_received_at` 统计。

> ⚠️ **风险提示（2026-08-08）**：`order.drawing_received_at` 字段是否已存在于订单表，§8.2标注"待确认"。这条口径切换功能和对应的验收标准目前当作已确定功能在描述，实际是否能实现取决于这个字段存不存在，评审时需要向研发确认，不要当成已落地功能对待。

#### 3.2.4 汇总卡（4 张）

| 卡片 | 公式 |
|---|---|
| 销售总额 | `SUM(amount WHERE direction=income AND fund_status=received)` |
| 退款总额 | `SUM(amount WHERE direction=expense AND fund_status=refunded)` |
| 坏账金额 | `SUM(amount WHERE direction=income AND fund_status=bad_debt)` |
| 净销售额 | 销售总额 - 退款总额（坏账已通过`fund_status=received`的筛选条件被排除，不需要在这里再减一次；2026-08-08修正：原公式"销售总额-退款总额-坏账金额"重复扣减了坏账，导致净销售额被低估） |

#### 3.2.5 列表字段（6 列）

| # | 字段 | 公式 |
|---|---|---|
| 1 | 维度值 | GROUP BY 的 key |
| 2 | 销售订单数 | `COUNT(DISTINCT order_id WHERE direction=income AND fund_status=received)` |
| 3 | 销售总额 | 同汇总卡 |
| 4 | 退款笔数 | `COUNT(* WHERE direction=expense AND fund_status=refunded)` |
| 5 | 退款总额 | 同汇总卡 |
| 6 | 净销售额 | 销售总额 - 退款总额（同§3.2.4修正，坏账不重复扣减） |

最后一行"合计"汇总所有维度行。

#### 3.2.6 规则约束

- 销售总额只算 `received` 的钱，**不包含** `pending` / `reversed` / `bad_debt`
- 退款总额只算 `refunded` 的，**不包含** `failed` / `pending`
- 部分退款的订单按 1 笔算，金额按实际退款算
- 全额退款的订单：原收入改 `reversed`，新支出记 `refunded`，**不计入**销售总额

#### 3.2.7 异常情况

| 场景 | 处理方式 |
|---|---|
| 铸件无来图时间（标准件/软件订单） | 不可切换到"来图时间"维度，仅"支付时间" |
| 维度切换后某分类无数据 | 显示空状态"暂无符合条件的数据" |
| 切换时间口径后总数变化 | 顶部汇总卡实时更新，列表同步刷新 |

### 3.3 模块三：支出统计

#### 3.3.1 功能描述

聚焦"钱出去了"的所有记录。展示所有退款的明细，区分 4 种退款类型 × 4 种退款状态。

#### 3.3.2 列表字段（11 列）

| # | 字段 | 展示 | 来源 |
|---|---|---|---|
| 1 | 退款单号 | 蓝色 mono | `refund_id`（关联） |
| 2 | 退款时间 | 时间降序 | `refund_time` |
| 3 | 退款类型 | 4 色 pill | `refund_type` |
| 4 | 退款状态 | 4 色 pill | `fund_status` |
| 5 | 退款金额 | 红色，右对齐 | `amount` + `direction=expense` |
| 6 | 原支付金额 | 灰色，参考用 | 原 `payment.amount` |
| 7 | 关联原订单 | 蓝色 mono，跳转 | `order_id` |
| 8 | 原支付方式 | 彩色 pill | 原 `pay_method` |
| 9 | 客户/企业 | 文本 | `customer_name` |
| 10 | 退款原因 | 客户填的或系统生成 | `remark` |
| 11 | 操作 | 详情 / 重试 / 催促 | — |

#### 3.3.3 退款类型（4 种）

| 枚举值 | 中文 | 触发场景 |
|---|---|---|
| `cancel_paid` | 客户取消已支付订单 | 客户在订单未发货前取消，自动触发 |
| `refund_partial` | 售后部分退款 | 售后申请部分商品退款 |
| `refund_full` | 售后全额退款 | 售后申请全部商品退款 |
| `adjustment` | 平台/财务调账 | 财务手动补差 |

#### 3.3.4 退款状态（4 种）

| 枚举值 | 中文 | 含义 |
|---|---|---|
| `pending` | 待退款 | 退款单创建，等待通道处理 |
| `processing` | 退款中 | 通道处理中 |
| `refunded` | 已退款 | 退款成功 |
| `failed` | 退款失败 | 通道返回失败，需人工重试 |

#### 3.3.5 汇总卡（4 张）

| 卡片 | 公式 |
|---|---|
| 退款总额 | `SUM(amount WHERE direction=expense AND fund_status=refunded)` |
| 待处理 | `COUNT(* WHERE direction=expense AND fund_status IN (pending, processing))` |
| 退款失败 | `COUNT(* WHERE direction=expense AND fund_status=failed)` |
| 涉及订单数 | `COUNT(DISTINCT order_id WHERE direction=expense)` |

#### 3.3.6 规则约束

- 部分退款：原 `payment_id` 关联的收入记录**不修改**，只新增一条支出流水
- 全额退款：原收入记录 `fund_status` 改 `reversed`，同时新增一条支出 `refunded`
- 退款失败可点击"重新退款"重试，成功后状态置 `refunded`
- 退款原因必填（客户填的或系统自动）

#### 3.3.7 异常情况

| 场景 | 处理方式 |
|---|---|
| 退款失败 | 操作栏显示"重新退款"按钮，财务可手动重试 |
| 平台调账退款 | `refund_type=adjustment`，退款原因填"调账-补差"等 |
| 多次部分退款 | 每笔退款单独立存在，按时间倒序排列 |

## 4. 核心流程

### 4.1 资金流水触发规则（关键）

```
订单创建（待支付）     → ❌ 不记流水
订单创建（已支付）     → ❌ 不记流水
支付成功（在线）       → ✅ income / received
支付成功（线下，审核通过）→ ✅ income / received
账期支付 - 客户实际打款 → ✅ income / received
订单取消（未支付）     → ❌ 不记流水
订单取消（已支付）     → ✅ expense / refunded
售后部分退款           → ✅ expense / refunded（**原收入记录不改**）
售后全额退款           → ✅ expense / refunded + 原收入 → reversed
财务调账（补收）       → ✅ income / received
财务调账（补退）       → ✅ expense / refunded
坏账勾销（账期到期）   → ✏️ income: received → bad_debt（**财务直接做，无审批**）
催收回款（坏账已勾销后）→ ✅ 新建 income / received（不挂原支付单）
```

### 4.2 坏账勾销流程

```
账期 30 天到期 → 客户未还 → 财务点击「坏账勾销」按钮
   ↓
fund_flow: fund_status = received → bad_debt
remark = "已坏账勾销 by 财务XXX" + 时间戳
   ↓
销售统计：销售总额自动剔除该笔 → 进入"坏账金额"卡
```

**关键决策：**
- 账期 30 天到期即可勾销
- **不需审批**，财务直接做
- 勾销后不可逆（除非走特殊恢复流程，留痕）

### 4.3 部分退款流程

```
客户申请售后部分退款
   ↓
创建 refund 记录，refund_type = refund_partial
   ↓
创建支出流水：direction=expense, fund_status=refunded
   amount = 本次退款金额（**原收入记录不改**）
   ↓
统计：销售总额 = SUM(received) - 不变
      退款总额 += 本次退款金额
      净销售额 = 销售 - 退款（坏账不重复扣减，见§3.2.4）
```

**为什么不改原收入？** 对账时要找到原始入账金额，原记录 + 后续支出记录可推算净额。

## 5. 数据结构

### 5.1 资金流水表 `fund_flow`

详见 [3.1.2 字段说明](#312-字段说明数据库表-fund_flow30-字段--7-组)。

**唯一索引：**
- `flow_id`（主键）
- `flow_no`（业务编号唯一）
- `(order_id, direction, fund_status, refund_id)`（避免同一笔支付/退款事件被重复记账；2026-08-11修正：原来是`(order_id, direction, fund_status)`三个字段，会导致同一订单的第二次部分退款insert时唯一索引冲突失败——因为两次退款的`order_id`/`direction=expense`/`fund_status=refunded`完全相同，只有`refund_id`不同。见§3.3.7"多次部分退款"场景，每笔退款是独立记录。income方向的记录`refund_id`为空，不受影响）

**查询索引：**
- `(customer_id, fund_time)` 客户维度
- `(category, channel, fund_time)` 销售统计聚合
- `(fund_status, fund_time)` 状态筛选

### 5.2 关联实体

| 关联表 | 关联字段 | 备注 |
|---|---|---|
| `order` | `order_id` | 订单主数据 |
| `payment` | `payment_id` | 支付单（收入用本笔，支出用原） |
| `refund` | `refund_id` | 退款单（仅支出时） |
| `settlement` | `settlement_id` | 结算单（可选） |
| `statement` | `statement_id` | 对账单（可选） |

## 6. 非功能性需求

| 类型 | 要求 |
|---|---|
| **数据准确性** | `amount` 永远正数，由 `direction` 区分方向；对账时不允许正负号混用 |
| **性能** | 收支明细列表查询响应 < 500ms（10w 行内）；销售统计聚合 < 2s |
| **可扩展性** | 资金状态机可扩展（新增状态不影响历史数据） |
| **可追溯** | 所有修改留痕（`updated_by` / `updated_at` / `remark`） |
| **权限** | 财务可勾销坏账；销售/运营只读，不可修改资金状态 |
| **审计** | 关键操作（坏账勾销、调账）必须填 `remark` 留痕 |
| **兼容性** | 旧版"按订单创建时间"销售统计保留为高级筛选，不影响新版默认 |

## 7. 验收标准

### 7.1 资金流水验收

- [ ] 待支付、已取消的订单**不出现**在收支明细页
- [ ] 列表展示 9 列字段，与原型一致
- [ ] "仅收入/仅支出" Tab 切换正确
- [ ] 导出 Excel 按当前筛选条件
- [ ] 流水编号格式 `LSyyyymmddXXXXX` 唯一

### 7.2 销售统计验收

- [ ] 4 个维度（按时间/客户/商品分类/支付方式/渠道）切换正常
- [ ] 铸件可切换"支付时间/来图时间"双口径，标准件/软件不可切换
- [ ] "全部" = 标准件 + 铸件 + 软件 三类汇总
- [ ] 坏账金额从销售总额中剔除，不重复计入
- [ ] 净销售额 = 销售总额 - 退款总额（坏账不重复扣减，见§3.2.4修正说明）
- [ ] 最后一行"合计"汇总所有维度行

### 7.3 支出统计验收

- [ ] 11 列字段展示与原型一致
- [ ] 4 种退款类型 × 4 种退款状态 全部覆盖
- [ ] 退款失败显示"重新退款"按钮
- [ ] 部分退款时原收入记录不变
- [ ] 退款原因必填

### 7.4 数据一致性验收

- [ ] 同一订单的"部分退款"产生独立的支出流水，原收入记录 `fund_status` 保持 `received`
- [ ] 同一订单的"全额退款"产生一条支出 + 原收入改 `reversed`
- [ ] 账期客户实际打款才产生 `received` 流水，账期台账扣减额度同步
- [ ] 坏账勾销后销售统计自动剔除该笔
- [ ] 催收回款新建独立 `received` 流水，不挂回原支付单
